ENGINE ARCHITECTURE

How Steadfast Guarantees Exactly-Once Effects

This 6-stage lifecycle explains how Steadfast guarantees zero lost jobs, zero double charges, and fenced zombie writes under crashes and network partitions:

1. Worker Claims Job
Worker claims the job atomically using PostgreSQL SELECT FOR UPDATE SKIP LOCKED. State transitions from QUEUED → LEASED.
2. Lease & Fencing Token Assigned
The engine assigns an exclusive lease deadline (e.g. 10s) and a strictly monotonically increasing Fencing Token (Token #1). Downstream systems require this token to reject stale attempts.
3. Heartbeat Renews Lease
While processing, the worker sends periodic heartbeats every 2 seconds to report continued ownership, advancing lease_expires_at.
4. Worker Crashes or Lease Expires
If a worker crashes (SIGKILL, freeze, OOM, network break), heartbeats halt and the lease deadline expires.
5. Reaper Detects Expired Lease
An independent leader-elected Reaper process constantly queries lease_expires_at < now(). It revokes the dead worker's lease, makes the job eligible for Attempt #2, and increments the fencing token (Token #2). If the zombie worker ever wakes up, its write is rejected with 409 Stale Fencing Token.
6. Retry or Terminal Outcome
A healthy replacement worker executes Attempt #2, commits the transaction to the ledger, and transitions the job to SUCCEEDED. Unrecoverable tasks are quarantined in the Dead-Letter Queue (DEAD).
